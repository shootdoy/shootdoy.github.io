배포본에서 주석을 걷어낸다

주석이 121KB 인데 HTML 은 워커가 network-first 라 방문마다 다시 받는다. 걷어내니 422 → 302KB · gzip 전송 169 → 118KB (−30%) 다. 반면 공백까지 지워도 gzip 은 2KB 밖에 더 줄지 않고, 식별자 압축은 몇 KB 를 위해 첫 의존성(terser)을 들이는 일이라 하지 않는다 — 측정으로 좁힌 결론이다.

assemble() = 조립본 · dist() = 배포본이고 배포본은 조립본의 순수 함수라 두 벌이 갈라질 수 없다. 지우는 것은 주석뿐이고 주석 안 개행을 되돌려 넣어 배포본 줄 번호가 조립본과 같다 — 배포본에서 본 오류 줄을 소스에서 바로 찾을 수 있어야 한다는 것이 원래 «변환 금지» 의 근거였다.

제거기는 상태 기계다. 정규식으로 지우면 'https://…' 나 base64 의 /* 를 잘라 조용히 깨진다. 안전망 넷 — 문법 파싱 · 부분 수열 · 주석 흔적 없음 · 바이트 보존 — 에 배포본을 실제로 실행하는 interact 를 더했다. 넷 다 일부러 망가뜨려 잡히는 것을 확인했다.

v3.48.4 2026-08-22

renderAll 이 기록 UI 를 갱신하지 않던 버그

기록 탭이 새로고침마다 사라지는 진짜 원인. 저장과 복원은 처음부터 정상이었다 — 슛도이가 콘솔로 저장값 playRec:true 를 새로고침 전후 모두 확인했고, v3.48.3 의 저장 실패 메시지도 뜨지 않았다.

탭(#vH)을 여닫는 코드는 renderHCur() 안에만 있는데, 그 함수는 파스 시점 한 번(playRec 이 아직 false 일 때)과 사용자 조작 때만 불렸다. load() 가 playRec 을 true 로 복원해도 아무도 다시 그려 주지 않아 탭이 감춰진 채 남았다. 그래서 켜면 나타나고 새로고침하면 사라졌다.

renderAll() 의 렌더 목록 끝에 renderHCur() 를 넣는다. 플레이 화면의 인라인 기록 블록(sPlayRecTop·sPlayRecBot)도 같은 이유로 안 나왔고 함께 고쳐진다.

jsdom 으로 두 판을 비교해 확인했다 — 빼면 hidden=true 로 남고, 넣으면 renderHCur ← renderAll 스택과 함께 hidden=false 가 된다. sync.js 짝 검사 2개 추가 (사보타주 확인).

v3.48.3 2026-08-22

저장이 조용히 실패하던 구멍을 막는다

«플레이 기록» 을 켜도 새로고침하면 꺼져 있다는 재지적. v3.48.0 의 flush 로는 안 끝났다. 증상 조합이 범인을 가리켰다 — 저장 상태줄은 «저장 켜짐» 이고 보유 태그와 기록은 남는데 설정만 사라진다.

saveWrite 첫 줄 savePayload() 가 try 밖이라, 값 하나가 상해 예외가 나면 saveWrite 가 거부되는데 save·saveFlush 가 await 없이 불러 아무도 잡지 않았다. backend 는 local 그대로여서 화면은 계속 «저장 켜짐» 이라 말하면서 그 뒤로 아무것도 저장되지 않는다. 기록은 HKEY 라 계속 저장돼 «설정만 안 남는다» 로 보였다.

세 겹으로 막는다 — bagArr 로 값 하나가 상해도 나머지는 저장 · saveFail 이 backend 를 내리고 실패 이유를 상태줄과 콘솔에 적음 · 호출 쪽에서 거부를 잡음.

무엇이 던지는지는 아직 모른다. 이제 이유가 화면에 뜨므로 다음 보고가 근거가 된다 — 모바일에는 콘솔이 없어 이것이 핵심이다. sync.js 검사 4개를 짝으로 넣고 사보타주로 확인했다.
